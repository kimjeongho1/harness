# record — 바뀐 것만 읽고, 사실만 쓴다

## 1. 시작할 때 (1회)
- AGENTS.md, README(과제 설명), `docs/` 를 읽는다.
- 과제가 정한 문서 이름·위치·질문 항목을 그대로 따른다. 없으면 `.harness/templates/`의 틀을 쓴다.
- 과제 폴더에 이미 있는 문서(예: 루트의 how_to_use.md)는 그 파일을 그 위치에서 채운다. `docs/`에 같은 문서를 새로 만들지 않는다.
- 뼈대만 만든다: `docs/DECISIONS.md`, `docs/HANDOFF.md`, 사용법 문서, AI 활용 문서. 내용은 비워 둔다.
- 마지막으로 읽은 커밋 해시를 HANDOFF.md 맨 아래 `last_read: <해시>`에, INBOX에서 옮긴 마지막 줄 번호를 `inbox_read: <번호>`에 적는다. INBOX는 A의 파일이다. C는 읽기만 한다.

## 2. "기록해: …" (사용자가 담당자 답·내 결정을 전달)
DECISIONS.md에 한 행 추가: `D-n | 결정 | 근거(담당자 답 원문·데이터·사용자 판단) | 버린 안 | 영향 | 코드 위치(미정이면 비움)`.
- 사용자가 AI 제안을 고친 경우 결정 칸을 "AI 제안 수정: AI 제안 → 내 결정 → 이유"로 적는다.
- 담당자 합의가 아닌 임시값은 "담당자 확인 전 임시값" 표에 적는다(값 / 이유 / 바꾸는 위치).
- 파일에는 대괄호 표시(`[가정]` 등)를 쓰지 않는다. 평범한 문장과 표로 적는다.
- 기존 결정과 모순되면 기존 행을 지우지 말고 `→ D-m으로 대체`를 표시한다.
- 담당자가 여럿이면 근거 칸에 누가 말했는지 쓰고, 말이 다르면 DECISIONS "담당자 의견이 다른 곳" 표에 적는다.
- 장애(접속 끊김·플랫폼 오류 등)는 AI 활용 문서에 `시각 | 증상 | 영향 | 한 일` 한 줄.

## 3. RECORD (커밋 2–3개마다)
0. `docs/INBOX.md`의 `inbox_read` 다음 줄부터 읽어 2번 규칙대로 DECISIONS·문서에 옮긴다(담당자 원문은 그대로).
1. `git log --oneline <last_read>..HEAD`, 필요한 것만 `git show --stat <해시>` / `git show <해시> -- <파일>`.
2. DECISIONS의 "코드 위치"를 채운다(파일:함수).
3. 사용법 문서: 실행 명령·화면·역할별 사용 흐름을 실제 코드 기준으로 갱신. **실행해서 확인한 명령만 적는다.** 확인 못 한 것은 문서에 쓰지 않고 채팅으로 "확인 필요: …"라고 사용자에게 알린다.
4. AI 활용 문서: 단계별로 AI에 맡긴 것 / 내가 한 것 / 받아들인·거절한 제안과 이유. 커밋 타임라인 표.
5. HANDOFF의 `## 구조`와 `## 핵심 결정과 약점`을 지금까지의 커밋 기준으로 갱신한다(마지막에 몰아서 쓰지 않는다. 서술형 준비가 된다).
6. `last_read`·`inbox_read` 갱신, 문서 파일만 커밋: `docs: D-n 반영, 사용법 갱신`.

## 4. 쓰는 법
- 모르는 "이유"는 지어내지 않는다. 문서에 비워 두지 말고 채팅으로 사용자에게 "왜 X를 골랐나요?"라고 묻는다. 답이 없으면 그 문장은 쓰지 않는다.
- 짧은 문장. "수행함·진행함·실시함" 대신 "함". "에 의해", "되어지다" 쓰지 않는다.
- 같은 모양 3항목 나열 반복, 과장, 이모지, "혁신적·획기적" 금지.
- 사실·숫자·결정 번호는 그대로 두고 말투만 다듬는다. (출처: epoko77-ai/im-not-ai 철칙 아이디어, MIT)

## 5. 마무리 (동결 후)
- 각 문서의 주장마다 근거(코드·커밋·실행 결과)가 있는지 대조. 없으면 고친다.
- **제출 전 점검**: `grep -rn "\[가정\]\|\[미검증\]\|\[사용자 결정 필요\]\|\[확인 필요" --exclude=AGENTS.md --exclude-dir=.harness --exclude-dir=.agents --exclude-dir=.git .` 결과가 0줄인지 확인(코드 포함). 있으면 사용자에게 알리고 정리한다(코드는 A에게 넘김).
- 끝내 실행하지 못한 검증은 HANDOFF 검증 표에만 `NOT_RUN`과 이유·확인 방법으로 한 행씩. 동결 전에 실행 가능한 것은 실행해서 3개 이하로.
- HANDOFF: 완료 / 미완료 / 알려진 한계 / 다음 행동 / 핵심 파일 / 실행 명령 / **검증 표**(검사 | 명령 | PASS·FAIL·NOT_RUN | 근거 위치 | 검사하지 않는 것)와 검사 코드 자체를 확인한 방법(일부러 넣은 위반이 잡혔는지). 데이터를 제외·보정했으면 이유·건수·전후 비교.
- 사용자 설명 준비 노트(채팅으로만): **아키텍처 한 장**(실제로 만든 구성요소만: 각 1줄 역할과 파일 위치, 요청·데이터 하나가 흐르는 순서), 핵심 결정 5개를 "결정 / 이유 / 버린 안 / 한계" 각 2줄, 가장 약한 부분 2개(약점 → 왜 위험한지 → 다음에 무엇을 검증·개선할지), AI가 틀렸던 지점 1개, 내가 직접 판단한 것 1개, 미검증 1개.
- 서술형 답 틀: 사실 → 결정(파일·함수) → 이유·버린 안 → 검증 결과 → 한계·다음 검증. 질문의 전제가 실제와 다르면 정정한다.
- 발표 1장(채팅으로만, 3분 분량): 현장 문제 → 담당자와 합의한 범위·성공 기준 → 방법과 버린 안 → 검증 숫자 → 한계와 다음 단계 → AI를 어떻게 통제했나(거절·축소한 제안 1개). + 예상 질문 5개와 각 2줄 답(기록에 있는 사실만).
