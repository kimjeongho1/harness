# design — 고르게 하고, 쪼개고, 그다음 만든다
출처(MIT): obra/superpowers `brainstorming`·`writing-plans`의 핵심만 요약·변형. 시각 도구·서브에이전트·스펙 파일 저장 단계는 쓰지 않는다.

## 1. 먼저 읽는다
README, 데이터 구조, `docs/DECISIONS.md`, 기존 코드를 읽고 지금 어떻게 되어 있는지 설명할 수 있을 때까지 본다. 문서에 답이 있는 건 묻지 않는다.

## 2. 접근법 2–3안 (이 메시지는 이것만)
| 안 | 핵심 | 장점 | 단점·위험 | 구현 난이도 | 남은 시간에 맞나 |
- 마지막 줄: `추천: X안 — 이유 한 줄`. 결과를 바꾸는 미정 기준이 있으면 `[사용자 결정 필요]`로 따로 적는다(→ clarify).
- 사용자가 고르기 전에는 **코드·파일을 만들지 않는다.**
- 고른 안과 버린 안은 INBOX에 `D-n | 고른 안 | 사용자 판단 '…' | 버린 안` 한 줄로 남긴다.
- 큰 작업을 맡기 전에 PLAN 작업마다 맥락(왜) / 만들 것 / 제약 / 완료 조건을 적는다.

## 3. PLAN.md로 쪼갠다 (A만 작성)
```
# PLAN  (선택: X안, D-n)
## 파일 책임
- app/...: 무엇을 담당
## 작업 (하나 = 커밋 하나, 15–25분)
- [ ] 1. <작업> | 완료 조건: <입력 → 기대 출력> | 검증: <명령>
```
- 순서: 과제가 요구한 구성요소를 가장 단순한 버전으로 **끝까지 연결**하는 것을 먼저, 개선은 뒤에.
- 요구에 없는 것은 넣지 않는다(YAGNI). 넣고 싶으면 "생략: X / 필요해지는 조건: Y".

## 4. 실행
작업 하나씩: 계획 3줄 → 테스트 또는 확인 명령 → 구현 → 실행 결과 → 체크박스 → 커밋. 막히면 AGENTS.md 규칙 11.
