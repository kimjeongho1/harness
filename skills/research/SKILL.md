# research — 짧게 찾고, 고르게 하고, 근거를 남긴다

## 규칙
- **10분 제한**(원문 읽기 포함 시 15분). 코드 금지.
- **논문 방법을 적용하려면 반드시 전문(원문)을 확보한다.** 후보를 좁힌 뒤 **최종 1~2편만**, 사용자에게 "이 논문 원문 볼까요? 이유: …" 승인을 받는다.
  - 확보 순서: ① HTML 전문(arXiv HTML판, 출판사 전문 페이지) ② 공개 PDF(arXiv 등)를 받아 텍스트로 변환 ③ 둘 다 안 되면 사용자에게 "브라우저로 열어 방법 절을 붙여 넣어 주세요" 요청.
  - PDF 변환 도구(`pdftotext` 등)가 있는지 먼저 확인한다. 없으면 설치하기 전에 사용자 승인을 받는다.
  - 전문을 확보하지 못한 논문은 **적용 근거로 쓰지 않는다**(비교표에 "초록만 확인"으로 남기고 후보에서 내린다).
  - 읽는 범위: 전문을 받되, 문제 정의·방법(알고리즘)·실험 조건(규모·제약)·한계 절을 읽는다. 서론·관련 연구는 건너뛴다. 읽은 뒤 **우리 과제와 같은 점 / 다른 점 / 그대로 쓸 것 / 바꿔야 할 것** 표를 만든다.
- 초록만 보고 방법을 적용하지 않는다.
- 먼저 이미 아는 지식으로 답한다. 웹 검색은 출처 확인이 필요할 때만, **최대 3회**.
- "논문 다 찾아봐"를 받아도 목록을 늘리지 않는다. **문제 유형 이름 → 그 유형의 표준 해법**으로 좁힌다.
- 출처 우선순위: ① 교과서·널리 인용되는 고전 논문 ② 표준 라이브러리·도구 공식 문서(예: 최적화 라이브러리 예제) ③ 그 밖. **무명 논문 1편을 근거로 방법을 고르지 않는다.**
- 모르는 출처를 지어내지 않는다. 확실하지 않으면 채팅에 "출처 미확인"이라고 쓴다.
- 비교에는 **가장 단순한 방법(규칙 기반·탐욕적 배정 등)을 반드시 1개** 넣는다.

## 출력 (이 형식만)
1. **문제 유형**: 이 과제가 알려진 어떤 문제와 같은가(이름 1~2개).
2. **해법 비교** (2~3개)
| 방법 | 원리 3줄 | 장점 | 단점 | 우리 제약에 맞나 | 구현 난이도 | 대표 출처(제목·저자·연도) | 확인 수준(지식·초록·원문) |
3. **이 방법이 정해주지 않는 값** → clarify 3-1 형식의 질문으로. 예: 최소·최대 수량, 한도, 목적 우선순위, 충돌 시 양보 순서, 기준 미달 처리.
4. **추천**: 단계별로.
   - L1 = 가장 단순하게 끝까지 동작하는 방법(먼저 구현)
   - L2 = 남은 시간에 개선할 방법
   - 점수표: 결과마다 출력할 숫자(예: 목적 값, 제약 위반 수, 기준 미달 수)
5. 마지막 줄: "어느 방법으로 갈까요?" 사용자가 고르기 전에는 설계·구현으로 넘어가지 않는다. 고르면 "C에게: D-n | 방법 선택 … | 근거: 사용자 판단 '…' + 출처 … | 버린 방법 …" 한 줄.
