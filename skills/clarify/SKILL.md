# clarify — 묻기 전엔 정하지 않는다
출처(MIT): github/spec-kit `templates/commands/clarify.md`(모호성 분류·한 번에 하나·답변 기록),
mattpocock/skills `grilling`("nothing left silently assumed", 사실 조회는 AI 몫),
obra/superpowers `brainstorming`(기본값은 말로 밝히고 'your call'로 표시, 승인 전 구현 금지),
bladem0117 cofa-kit `stakeholder-interview`(2차 왕복: 목적·제약·파라미터를 2~3안으로 고르게 함).
이 시험용 변경: Codex는 **사용자에게 직접 꼬치꼬치 묻는다.** 업무 규칙은 담당자에게 확인하도록 권하고 보낼 문장을 준다. 답은 기록한다.

## 1. 먼저 사실은 직접 찾는다
README, 데이터 파일, 기존 DECISIONS.md로 답할 수 있는 건 묻지 않는다. 데이터로 확인한 사실은 숫자로 적는다.

## 2. 미정 결정 스캔 (각 항목 Clear / Partial / Missing)
1. 범위·사용자 역할(누가 무엇을 하나, 범위 밖)
2. 데이터·엔티티(식별자, 상태 변화, 규모)
3. **하드 제약**(절대 위반 불가 숫자)
4. **소프트 제약**(가능하면 지킬 것, 위반 시 처리)
5. **충돌 시 우선순위**(무엇을 먼저 양보하나)
6. **임계값**(최소·최대 기준이 없는 규칙. 예: "너무 적으면 안 됨" → 몇 개?)
7. 예외 케이스와 처리(규칙을 지킬 수 없는 대상)
8. 자동 결정 vs 사람 승인
9. 개인정보·권한
10. 완료 기준(검증 가능한 숫자)
11. 정량화되지 않은 표현("많이", "적당히", "빨리")

## 3. 질문 방식 — 사용자에게 직접 묻는다
- Missing/Partial 중 **결과를 바꾸는 것만**, 영향이 큰 순서로. 코드를 쓰기 전에 묻는다.
- **한 번에 하나씩** 사용자에게 직접 묻는다. 형식:
  `Q1. <결정할 것> / 왜 중요: <한 줄> / 선택지: A(영향) · B(영향) · C(영향) / 내 추천: B, 이유`
- 업무 규칙(정책·우선순위·임계값)이면 끝에 **[담당자 확인 권장]**과, 담당자에게 보낼 한 문장을 붙인다.
- 기술 선택(라이브러리·구조)이면 추천안으로 진행해도 되는지 묻는다.
- 답을 받으면 다음 질문을 갱신한다. 사용자가 "알아서 해"라고 하면 추천안을 쓰되 '가정(내 판단)'으로 기록한다.

## 3-1. 논문·외부 방법을 적용할 때
논문이나 알고리즘을 토대로 로직을 짜라는 요청을 받으면, 구현 전에 **그 방법이 정해주지 않는 값**을 목록으로 만들어 위 형식으로 묻는다.
예: 최소·최대 수량, 거리·시간·용량 한도, 목적함수 가중치(비용 vs 편의), 규칙끼리 충돌 시 양보 순서, 기준 미달 결과 처리, 예외 대상 처리.
논문 기본값을 쓰려면 "논문 기본값: X (출처 쪽수) — 이 과제에 맞는지 확인 필요"로 밝히고 묻는다. 말없이 정하지 않는다.

## 3-2. 담당자 인터뷰 순서 (사용자가 묻는다. Codex는 질문 후보만)
담당자는 해결책을 모른다. **열린 질문("어떻게 할까요?") 대신 2~3안을 보여 주고 고르게** 한다.
1차(사실): 지금은 누가·언제·어떤 도구로 하나 / 최근 실제 사례 하나 / 가장 오래 걸리거나 자주 틀리는 단계 / 숫자 기준(정원·시간·거리) / 자동 vs 사람 승인 / 누가 어떤 정보를 볼 수 있나 / 꼭 필요한 것 vs 있으면 좋은 것.
2차(선택): 결과를 계산·추천·판정하는 로직이면 목적(무엇을 최소화)·제약·파라미터를 2~3안으로 만들어 담당자가 고르게 한다. "제약 없는 최적화는 이상한 결과를 낸다."
답을 받으면 **요약 → 확인 → 심화**: "그러니까 X가 제일 오래 걸린다는 거죠? 그럼 X에서 틀리면 어떤 일이 생기나요?"
해결책이나 작업 순서를 통째로 달라고 하지 않는다. 막히면: "제가 어떤 부분을 여쭤보면 도움이 될까요? 담당자님이 알려 주실 수 있는 범위가 궁금합니다."
README와 담당자 말이 다르면 그 충돌을 짚어 확인한다.
구현 후(L1 완성) 결과 확인 1회: "말씀하신 X 상황에서 이렇게 나옵니다(숫자·예시). 원하시던 것과 맞나요? 빠진 게 있을까요?"
마무리: 문제 / 역할별 니즈 / 성공 기준 / 안 할 것을 요약해 "맞나요?"로 확인.

## 4. 답변 기록
A·B는 DECISIONS를 직접 고치지 않는다. 답을 받으면 **C에게 전달할 한 줄**을 만들어 준다:
`C에게: D-n | 결정: … | 근거: 담당자 답 "…" | 버린 안: … | 코드 위치: (구현 후)`.
C는 DECISIONS.md에 기록하고, 기존 문장과 모순되면 교체한다(중복 금지).

## 5. 답을 못 받은 것
- 구현을 막는 하드 제약·우선순위는 **구현하지 않고 멈춘다**: `BLOCKED: <결정> 확인 필요`.
- 막지 않는 것은 임시값을 쓰되 **`[가정] 값 / 이유 / 바꾸는 위치`**로 채팅에서 표시하고(C에게 전달), 코드에서는 설정 상수로 분리한다. 코드·주석에는 표시를 쓰지 않는다. 담당자가 합의한 것처럼 쓰지 않는다.

## 6. 다시 쓰는 시점
구현 중 결과가 이상할 때(예: 기준 미달 결과, 규칙 위반, 예외 대량 발생) 이 스킬을 다시 실행한다. 원인이 "정하지 않은 기준"이면 알고리즘을 고치기 전에 질문부터 만든다.
